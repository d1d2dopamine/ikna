# Икна, Round62: приватные файлы синхронизации на Windows

## Причина падения

В переданном логе Windows приложение дошло до packaged selftest, но остановилось
в LanSyncSecurity.privatePermissions при сохранении конфигурации синхронизации.
Это следующий блокер после Round61. Наличие Unsafe уже подтверждено самим логом.
Отсутствие NSIS EXE является последствием остановившейся сборки, а не поводом
ослаблять проверку upload-artifact.

Старый код после неподдерживаемых POSIX-прав вызывал File.setReadable /
setWritable и проверял их результат. Такой fallback не устанавливает требуемый
Windows ACL и в указанной среде вернул false. Локально Windows не запускалась:
связь со сбоем установлена по стеку пользователя и исходному коду.

## Изменения

- POSIX: прежние точные режимы 0700 для каталога и 0600 для файла, с проверкой
  прочитанных обратно прав и сохранением владельца.
- Windows ACL: разрешение только текущей индивидуальной учётной записи, проверка
  владельца и полного списка ACL после установки. Остаточное широкое разрешение,
  неподдерживаемый провайдер или ошибка проверки останавливают операцию.
- Новые пустые объекты могут получить текущего владельца до записи секретов.
  В Windows ACL-ветке уже существующие объекты чужой учётной записи или
  группы не присваиваются.
- Родительский приватный каталог защищается до создания временного файла;
  ограниченные начальные права задаются одновременно с созданием. Секреты
  записываются только после проверки. Сохранены force и атомарная замена.
- Существующие ключи и конфигурация проверяются перед ограниченным чтением.
  Символические ссылки и Windows junction/reparse-point объекты отклоняются
  до изменения их прав; проверяется и непосредственный родитель при создании.
- Добавлен отдельный Windows CI-тест до сборки приложения. Существующие packaged
  selftest, строгая проверка EXE и NSIS-сборка сохранены.

Протокол, данные обучения, каталог карточек, UI и схема базы не меняются.

## Что проверено

Изолированный Kotlin/JUnit запуск: 18 тестов прошли, 0 ошибок; 3 нативных
Windows-теста пропущены по платформе Linux. Скомпилированы реальные
PrivateSyncFiles и LanSyncSecurity с Kotlin 2.2.20, JDK17 и реальной
OkHttp TLS зависимостью. Подменяются только
NIO-провайдеры в негативных тестах; POSIX операции выполняются на временных
синтетических файлах. Это не сборка всего приложения.

Все 13 Python-команд соответствующего шага grading workflow прошли локально.
Попытка обычного Gradle :shared:desktopTest остановилась до компиляции: окружение
не смогло разрешить com.android.application 8.6.1 из настроенных репозиториев.
Лог не скрыт и не засчитан как успешная сборка.

Нативные Windows тесты проверяют наследованные широкие ACL, повторное чтение,
атомарную замену, сохранение идентичности сертификата и отказ для junction без
изменения целевого каталога. На Linux они пропускаются по условию платформы.

## Пределы и следующий шаг

Нужен обычный Windows CI запуск этого архива: должны пройти новый ACL-тест,
сборка приложения, packaged selftest и создание/загрузка NSIS EXE. До этого
исправление не объявляется подтверждённым на Windows. Нового APK, установщика
или полного Gradle-тестирования этим раундом не подтверждено.

Ожидается доверенный каталог приложения. Проверки не защищают от администратора
или вредоносного процесса той же учётной записи, способного подменять предков
пути. Java setAcl/readback не равен постоянному запрету наследования DACL.
Синхронизация файла и атомарная замена не дают универсальной гарантии при
отключении питания: синхронизация каталога зависит от файлового провайдера.

Если в Windows ACL-ветке существующий приватный каталог принадлежит другой
учётной записи/группе,
код завершится с объяснением; не следует открывать права Everyone для обхода.
Автоматическая смена владельца существующих данных намеренно не выполняется.

Архив содержит полный накопленный исходный проект от Round61 и доказательства
проверок. Корпуса, временные ключи/конфигурация, зависимости и результаты сборки
не включены. Исходный файл подписи проекта сохранён без изменения.


## Воспроизведение и источники

Компактные результаты, хеши и изолированный runner:
`docs/evidence/private-sync-round62/isolated-jvm/`. Runner принимает `--repo`,
`--work-dir` и `--java-home`, проверяет JDK17 и хеши Maven-зависимостей.
Корпуса и данные пользователя для него не нужны. Весь проект проверяется
обычными Gradle/Windows CI командами, а не этим узким runner.

- [Java AclFileAttributeView](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/nio/file/attribute/AclFileAttributeView.html): ACL и зависимость отображения прав от файлового провайдера.
- [OpenJDK17 Windows ACL implementation](https://github.com/openjdk/jdk17u/blob/master/src/java.base/windows/classes/sun/nio/fs/WindowsAclFileAttributeView.java): установка DACL и ограничения интерфейса.
- [OpenJDK17 Windows file attributes](https://github.com/openjdk/jdk17u/blob/master/src/java.base/windows/classes/sun/nio/fs/WindowsFileAttributes.java): junction может быть каталогом без признака symbolic link, поэтому дополнительно проверяется isOther.
